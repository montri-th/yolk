# ปรับเกณฑ์ แล้วเห็นว่าไข่แดงเปลี่ยนตรงไหน

เป้าหมายของหน้านี้คือช่วยให้ทีมทดลองสมมติฐานได้ง่าย: ลากค่า ดูผลบนพื้นที่ อ่านเหตุผล แล้วค่อยใช้เกณฑ์กับทีม สูตรทั้ง 3 ธุรกิจ ข้อมูลต้นทาง และฐาน percentile ประเทศคงเดิมใน v1.6

## วิธีใช้

1. เลือกธุรกิจ แบรนด์ และ Supply scope เพื่อเปิด draft ของบริบทนั้น
2. เปิดแท็บ **Demand / Supply / รูปแบบ / น้ำหนัก** ปรับแถบเลื่อนหรือกรอกค่า แผนที่ยังอยู่ให้เทียบผล
3. ดูยอดเกณฑ์ทีม → แบบร่าง แล้วสลับ **เข้าใหม่ / หลุดเกณฑ์** เพื่อดูผลที่ซ่อนอยู่หลังยอดสุทธิ
4. เลือกจังหวัดเพื่อดูรายชื่อทำเล กดทำเลเพื่ออ่าน Tier, Supply และสถานะภายใต้ draft การเปิด detail ใช้เกณฑ์ทีมที่บันทึกแล้วและมีข้อความบอก
5. กด **คืนค่า** หากไม่ใช้ draft หรือ **ใช้เกณฑ์นี้กับทีม** เมื่อพร้อมบันทึก revision ใหม่

Desktop ให้ตัวปรับค่าและแผนที่ใช้ความสูงหน้าจอร่วมกัน ตัวปรับค่าเลื่อนแยก แผนที่ซูม/เลื่อนได้และคงมุมมองขณะปรับ บนมือถือใช้แผนที่ย่อที่คงอยู่และปุ่มเปิดรายชื่อทำเล รองรับ touch, mouse และ keyboard โดยใช้ความหมายเดียวกันทั้งไทย/อังกฤษ

## อ่านแผนที่ให้ตรงกับข้อมูล

| มุมมอง | ชุดทำเลที่แสดง | สิ่งที่ต้องอ่าน |
|---|---|---|
| ผ่านเกณฑ์ | `draft.eligible === true` | พื้นที่ที่ยืนยันว่าตรงเกณฑ์ทีมตาม draft |
| เข้าใหม่ | ผ่าน draft แต่ไม่อยู่ในชุดผ่านของ revision ทีม | ตัวเลข `+` และชื่อทำเล |
| หลุดเกณฑ์ | ผ่าน revision ทีม แต่ไม่อยู่ในชุดผ่านของ draft | ตัวเลข `−` และชื่อทำเล |
| รอตรวจ | `draft.reviewCandidate === true` | ลายเฉียง; ไม่รวมในยอดผ่านยืนยัน |
| อันดับ | ผ่านทั้งสองชุดและอันดับเปลี่ยน | ตัวเลข `↕` และอันดับทีม → แบบร่าง |

ผลต่างคำนวณจาก **UUID** ไม่ใช่ยอดสุทธิ เช่น เข้าใหม่ 10 และหลุด 10 ต้องเห็นทั้งสองชุด แม้จำนวนรวมเท่าเดิม อันดับเทียบภายในรายชื่อที่ผ่านเกณฑ์แต่ละชุด การเปลี่ยนสมาชิกอาจทำให้อันดับของทำเลเดิมเลื่อนด้วย จึงไม่เรียกทุกการเลื่อนว่าเกิดจาก weight เพียงอย่างเดียว

แผนที่ใช้ขอบเขต **จังหวัด** จริง 77 แห่งและสรุปทำเลลงจังหวัด ไม่ใช่ boundary ของทั้ง 7,954 แขวง/อปท. Badge อยู่ตำแหน่งสรุปของจังหวัด ไม่ใช่พิกัดสาขา และอาจซ่อนบาง badge เมื่อชิดกัน; เลือกจังหวัดหรือรายชื่อเพื่ออ่านจำนวนครบ

สีในชั้นผ่าน/เข้าใหม่/หลุดใช้ percentile ของ Demand signal เด่นสุดในกลุ่มที่แสดง: `<P95`, `P95–<P99`, `P99–P100` ตามสี LDS เดิมบนทั้งสองธีม หากไม่มีทำเลใน layer ใช้พื้นกลาง ไม่ได้สรุปว่าจังหวัดไม่มีตลาด สีและจำนวนตอบคนละคำถาม: ลดจำนวนแล้วสีอาจเหมือนเดิมได้ มุมมองอันดับใช้ `↕` และตัวเลข ไม่แปลงสี Demand เป็นคะแนน rank

## ตัวปรับค่าและการบันทึก

| ค่า | แถบเลื่อน | ช่องกรอก |
|---|---|---|
| Percentile | P1–P100 ขั้นละ 1 | กรอกค่าละเอียดตาม validator เดิม เช่น P99.7 |
| จำนวนเงื่อนไขผ่าน | 1–จำนวน metrics ในกลุ่ม | คงขอบเขต input/validator เดิม; บอกหากค่านอกช่วงแถบเลื่อน |
| Supply เริ่ม “มาก” | ช่วงตาม input เดิม เริ่ม 1–100 | กรอกจำนวนเต็ม |
| น้ำหนัก | 0–100 ขั้นละ 1 | กรอกค่าได้ตาม validator; น้ำหนัก 0 เป็นค่าจริง ไม่ใช่ข้อมูลขาด |

แถบเลื่อนและช่องกรอกแทนค่าเดียวกัน ช่องว่างต้องคงสถานะไม่ครบ ห้ามเติม 0 เงียบ ๆ ค่าไม่ถูกต้องให้พักผลแผนที่และปิด Apply ไม่แสดงผลเก่าเป็นผลของ draft ที่ยังใช้ไม่ได้ น้ำหนักใช้เรียงอันดับเท่านั้น; สำหรับ context ranking หมวด weight จะบอกว่าต้องเลือกวิธีเรียงตามน้ำหนักก่อน

ระหว่างลาก update ค่า input ทันที แล้วรวมงานคำนวณ/แสดงผลประมาณทุก **120ms**; `change` flush ค่าสุดท้าย ตรวจ route/context ก่อนใช้ผล รักษา node ของ input เพื่อไม่เสีย focus หรือจังหวะลาก การเปลี่ยน metric ที่ต้องสร้างตัวปรับใหม่ต้องติดตั้ง control และ label กลับให้ครบ

Draft เป็นส่วนตัวและแยกตาม `workspace + industry + ownEntity + format/product + profileVersion` ธีม ภาษา การดูจังหวัด การเปลี่ยนแท็บ และการปรับ draft ไม่สร้างกิจกรรมทีม Apply ที่สำเร็จเท่านั้นเพิ่ม revision/event หนึ่งครั้ง หากบันทึกไม่สำเร็จหรือ revision ขัดแย้งให้เก็บ draft ไว้

## จุดรับงานสำหรับ dev

แยกงานตามลำดับและใช้ [machine contract](../contracts/criteria-workspace.v1.6.1.json) ประกอบ:

1. ต่อ layout และ tab semantics โดยไม่แก้ evaluator หรือ preset
2. ต่อ range → input เดิม และ input → range พร้อม labels/disabled/invalid
3. สร้าง ID-set diff และ rank map จากผล evaluator เดิม
4. ต่อจังหวัด/map/list/inspector ด้วย snapshot เดียวกันและรักษา zoom
5. ต่อ throttle, flush และ context guard; ตรวจ draft/Apply event boundary
6. รัน focused checks และตรวจภาพจริงแยกจาก hash/source checks ก่อนปล่อยรุ่น

Focused checks ที่มีใน repo: `node scripts/check-criteria-controls.cjs`, `node scripts/check-criteria-map.cjs` ร่วมกับ release gates เดิม ผลรันและภาพ browser ต้องบันทึกใน release evidence ตามจริง เอกสารนี้ไม่อ้างว่าตรวจครบทุก device แล้ว

ต้องตรวจอย่างน้อย: เข้า/หลุดเท่ากันแต่ ID ต่างกัน, weight-only membership คงเดิม, review ไม่ปน confirmed, invalid input พักผล, context switch ไม่รับผลเก่า, ปล่อย slider ได้ค่าสุดท้าย, metric replacement ไม่ทำ slider หาย, keyboard focus, Thai/English ที่ desktop และจอแคบในสองธีม

## เส้นทาง production

Preview คำนวณใน browser และจำลองการทำงานร่วมกันผ่าน browser storage ยังไม่มี API หรือ worker ที่ยืนยันใช้งาน production การขยายระบบควรทำต่อจาก stack ที่สำรวจใน Task 00:

- ส่งงานคำนวณพร้อม `requestId`, `contextKey`, `sourceReleaseId`, `cohortHash`, `baseRevision` และ `draftHash`
- ยอมรับเฉพาะผลล่าสุดที่ยังตรงบริบท ยกเลิกงานเก่าเมื่อทำได้; server/worker กับ UI ต้องไม่แข่งกันเขียน snapshot
- Cache baseline ของ revision ทีมตาม source/cohort/scope แยกจาก draft และไม่ rebase percentile เมื่อกรองจังหวัด
- Server validate และ revision lock ก่อน transaction ของ criteria revision + event + outbox; notification dedupe ตาม event ID
- เพิ่ม actual area polygons เฉพาะที่มี provenance และ crosswalk ที่ยืนยันแล้ว การมี extent ไม่เพียงพอให้วาด boundary

แต่ละงานต้องระบุว่า reuse module ไหน ใช้ source release ใด และผ่าน acceptance ข้อใด ไม่ถือว่าการทดลอง static preview เท่ากับต่อ production สำเร็จ


### ขยายพื้นที่ทำงานบน desktop

กด **ขยายพื้นที่ทำงาน** เพื่อใช้เกณฑ์กับแผนที่เต็มพื้นที่หน้าจอ ยังลากค่าและใช้กับทีมได้ในมุมมองเดียว กด **กลับหน้าปกติ** หรือ Escape เพื่อกลับ แยกการซูม/เลือกจังหวัดออกจากการเปลี่ยนเกณฑ์ การเปิดเมนูธุรกิจให้คำนวณพื้นที่ว่างใหม่โดยไม่เปลี่ยน cohort
